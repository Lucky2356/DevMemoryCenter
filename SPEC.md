# Главный промт проекта Dev Recall

Ты являешься ведущим разработчиком, архитектором, специалистом по безопасности, тестировщиком и техническим писателем проекта **Dev Recall**.

Твоя задача — последовательно разработать качественное кроссплатформенное desktop-приложение для Windows и Linux.

Не пытайся реализовать весь проект за один шаг. Сначала подготовь архитектуру, структуру репозитория, документацию и план. Затем реализуй проект небольшими проверяемыми этапами.

После каждого этапа обязательно:

1. Запускай форматирование.
2. Запускай линтеры.
3. Запускай тесты.
4. Проверяй сборку.
5. Выполняй предусмотренные проверки безопасности.
6. Обновляй `TODO.md`.
7. Обновляй `PROJECT_STATE.md`.
8. Создавай небольшой Git-коммит только после успешных проверок.
9. Не переходи к следующему этапу, если текущий этап оставляет проект в неработоспособном состоянии.

# 1. Название продукта

Рабочее название:

**Dev Recall**

Подзаголовок:

**Local memory for developers and system administrators**

Русское описание:

**Локальная память рабочего процесса разработчика и системного администратора.**

---

# 2. Назначение продукта

Dev Recall помогает разработчикам и системным администраторам восстанавливать контекст работы над локальными проектами.

Приложение должно отвечать на вопросы:

* На чём я остановился?
* В какой ветке работал?
* Какие команды запускал?
* Какая команда завершилась ошибкой?
* Как я исправлял похожую проблему раньше?
* Какие контейнеры и локальные сервисы использовались?
* Какие порты были открыты?
* Какие изменения произошли во время рабочей сессии?
* Что было сделано за день?
* Какой следующий шаг был запланирован?
* Как воспроизвести удачную последовательность команд?
* Когда проблема появилась впервые?
* Какой коммит или команда предшествовали проблеме?

Приложение не должно быть полноценным IDE, терминалом, Docker-клиентом, Git-клиентом, системой удалённого администрирования или системой мониторинга серверов.

Dev Recall должен собирать, связывать, структурировать и отображать локальный рабочий контекст.

---

# 3. Главный принцип

Продукт должен работать по принципу:

> Читать и объяснять — безопаснее, чем автоматически изменять и выполнять.

По умолчанию Dev Recall:

* не выполняет найденные команды;
* не подключается к удалённым серверам;
* не хранит SSH-ключи;
* не хранит пароли;
* не отправляет данные в интернет;
* не загружает пользовательские файлы в облако;
* не использует телеметрию без отдельного явного согласия;
* не читает содержимое исходного кода без необходимости;
* не индексирует весь диск;
* не требует административных прав;
* не запускается с повышенными привилегиями;
* не использует искусственный интеллект;
* не принимает решения за пользователя.

Команда может быть выполнена только после явного действия пользователя и только в будущей специально спроектированной версии. В первой версии выполнение команд запрещено.

# 5. Выбранный технологический стек

## Основной язык

Использовать:

* Rust stable;
* Rust edition, актуальную для стабильной версии на момент создания проекта;
* преимущественно Safe Rust.

Применение `unsafe` запрещено, кроме случаев, когда оно неизбежно из-за системного API и полностью обосновано.

Каждое применение `unsafe` должно:

* быть минимальным;
* находиться в изолированном модуле;
* сопровождаться комментарием `SAFETY`;
* иметь тесты;
* быть отражено в `SECURITY.md`;
* пройти отдельный архитектурный анализ;
* не добавляться только ради оптимизации.

## Desktop framework

Использовать:

* Tauri 2;
* React;
* TypeScript;
* Vite.

## Стили интерфейса

Использовать один из вариантов:

* CSS Modules;
* Tailwind CSS;
* другой небольшой и хорошо обоснованный подход.

Не добавлять тяжёлую UI-библиотеку без необходимости.

## Локальная база

Использовать SQLite.

Требования:

* миграции базы;
* внешние ключи;
* параметризованные запросы;
* транзакции;
* ограничения целостности;
* индексы;
* WAL только после тестирования поведения на Windows и Linux;
* ограниченный connection pool;
* контроль размера WAL;
* периодический безопасный checkpoint;
* резервное копирование пользовательской базы;
* восстановление после повреждения;
* версия схемы;
* проверка совместимости миграций.

Рекомендуемый Rust-слой:

* `sqlx` с SQLite;
* либо другой зрелый поддерживаемый crate после документированного сравнения.

## Асинхронность

Использовать Tokio только там, где асинхронность действительно необходима.

Не создавать:

* бесконтрольные фоновые задачи;
* вечные циклы без cancellation token;
* бесконечные очереди;
* неограниченные каналы;
* лишние потоки;
* таймеры с чрезмерной частотой опроса.

Все фоновые задачи должны корректно останавливаться при завершении приложения.

# 7. Основные функции MVP

## 7.1. Управление проектами

Пользователь может:

* добавить локальную папку проекта;
* удалить проект из Dev Recall без удаления файлов проекта;
* переименовать отображаемое название;
* присвоить проекту цвет или значок;
* добавить теги;
* указать описание;
* архивировать проект;
* закрепить проект;
* открыть папку в системном файловом менеджере;
* открыть проект в выбранном редакторе;
* вручную обновить состояние проекта.

Приложение должно автоматически определять:

* наличие Git-репозитория;
* корень Git-репозитория;
* текущую ветку;
* последний коммит;
* наличие незакоммиченных изменений;
* тип проекта по безопасным маркерам;
* наличие Docker Compose;
* наличие известных manifest-файлов.

Не читать все файлы проекта.

Для определения типа проекта разрешено проверять только ограниченный список маркерных файлов:

* `Cargo.toml`;
* `go.mod`;
* `package.json`;
* `pyproject.toml`;
* `requirements.txt`;
* `pom.xml`;
* `build.gradle`;
* `docker-compose.yml`;
* `compose.yml`;
* другие явно поддерживаемые manifest-файлы.

## 7.2. Рабочие сессии

Пользователь может:

* начать рабочую сессию;
* приостановить сессию;
* возобновить сессию;
* завершить сессию;
* добавить краткую цель;
* добавить заметку;
* указать следующий шаг;
* просмотреть продолжительность;
* увидеть связанные команды, Git-события и ошибки.

Приложение не должно использовать активность мыши или клавиатуры для слежения за пользователем.

Не реализовывать кейлоггер.

Не записывать нажатия клавиш.

Не делать скриншоты.

Не захватывать буфер обмена без явного действия пользователя.

Не определять содержимое открытых окон.

## 7.3. Terminal Memory

Поддерживать импорт истории из:

* PowerShell;
* Bash;
* Zsh;
* Git Bash;
* Windows Command Prompt, если история доступна безопасным способом;
* WSL.

Команда должна связываться, когда информация доступна, с:

* проектом;
* рабочим каталогом;
* временем;
* оболочкой;
* платформой;
* Git-веткой;
* рабочей сессией;
* кодом завершения;
* длительностью выполнения.

В первой версии допустимо, что часть метаданных будет отсутствовать при обычном импорте history-файлов.

Не пытаться скрыто внедряться в оболочку.

Любая shell-интеграция должна:

* устанавливаться только по явному запросу пользователя;
* заранее показывать точные изменения;
* иметь возможность полного удаления;
* не ломать пользовательские конфигурации;
* создавать резервную копию изменяемого shell profile;
* использовать отдельный маркированный блок;
* быть идемпотентной;
* не записывать stdout и stderr команд по умолчанию;
* не перехватывать пароли;
* не сохранять ввод интерактивных приложений.

## 7.4. Поиск

Поддерживать локальный поиск по:

* командам;
* проектам;
* тегам;
* заметкам;
* веткам;
* кодам завершения;
* рабочим каталогам;
* типам оболочки;
* датам;
* рабочим сессиям.

Первая версия не использует нейронные сети и embeddings.

Использовать:

* полнотекстовый поиск SQLite FTS5, если это безопасно и поддерживается выбранной поставкой;
* токенизацию;
* нормализацию;
* fuzzy-поиск с ограничениями;
* фильтры;
* историю запросов, отключаемую пользователем.

Поиск должен быть быстрым на базе, содержащей не менее одного миллиона записей команд.

## 7.5. Избранные команды

Пользователь может:

* добавить команду в избранное;
* добавить безопасное описание;
* добавить теги;
* указать платформу;
* указать оболочку;
* указать проект;
* скопировать команду;
* посмотреть, когда она использовалась;
* создать шаблон с параметрами.

Пример шаблона:

```text
docker logs --tail {{lines}} {{container}}
```

Подстановка параметров не должна автоматически запускать команду.

## 7.6. Timeline

Отображать единую временную шкалу:

* начало и завершение рабочей сессии;
* импортированные команды;
* Git checkout;
* Git commit;
* изменение статуса рабочей директории;
* ручные заметки;
* обнаруженные локальные контейнеры;
* запуск или остановку локального процесса, только если пользователь включил соответствующее наблюдение;
* ошибки команд;
* важные изменения состояния.

Не создавать чрезмерно подробную ленту.

Должны быть:

* группировка похожих событий;
* фильтры;
* сворачивание;
* дневной и проектный режимы;
* пагинация или виртуализация;
* ограничение объёма загружаемых данных.

## 7.7. Git-контекст

Работать с Git преимущественно через библиотеку или безопасный вызов бинарника без shell-интерпретации.

Показывать:

* ветку;
* последний коммит;
* локальные изменения;
* последние коммиты;
* теги;
* связь коммитов с рабочими сессиями.

Не выполнять автоматически:

* commit;
* push;
* pull;
* fetch;
* checkout;
* reset;
* clean;
* rebase;
* merge;
* изменение remotes.

Не читать и не сохранять Git credentials.

## 7.8. Docker-контекст

В MVP Docker-интеграция является необязательной и только читающей.

Разрешено показывать:

* наличие Docker;
* локальные контейнеры, связанные с проектом;
* состояние контейнеров;
* используемые локальные порты;
* image name;
* compose project;
* время запуска.

Запрещено автоматически:

* запускать контейнеры;
* останавливать контейнеры;
* удалять контейнеры;
* читать secrets;
* читать значения переменных окружения контейнера;
* подключаться к удалённому Docker daemon;
* монтировать Docker socket внутрь сторонних процессов.

## 7.9. Порты и процессы

Опционально показывать:

* локальные слушающие порты;
* процесс-владелец;
* PID;
* локальный интерфейс;
* принадлежность известному проекту.

Не завершать процессы.

Не изменять firewall.

Не сканировать локальную сеть.

Не сканировать внешние адреса.

Не выполнять port scanning.

Не требовать административных прав ради дополнительных сведений.

# 8. Работа с секретами и чувствительными данными

История терминала может содержать:

* токены;
* пароли;
* API-ключи;
* строки подключения;
* cookies;
* персональные данные;
* внутренние адреса;
* секреты облачных провайдеров;
* приватные URL;
* данные авторизации в командах.

Поэтому необходимо реализовать обязательную систему защиты.

## 8.1. Secret redaction

Перед сохранением команда должна проходить локальный redaction pipeline.

Обнаруживать как минимум:

* `password=`;
* `passwd=`;
* `pwd=`;
* `token=`;
* `api_key=`;
* `apikey=`;
* `secret=`;
* `access_key=`;
* `client_secret=`;
* `Authorization: Bearer`;
* Basic Auth в URL;
* GitHub tokens;
* GitLab tokens;
* AWS access keys;
* private key blocks;
* JWT;
* database connection strings;
* пароли в CLI-аргументах;
* cookies;
* распространённые форматы облачных credentials.

Вместо секрета сохранять:

```text
<REDACTED>
```

Не сохранять исходное значение даже временно дольше, чем требуется для обработки.

Не писать исходную команду с секретом в лог.

Не помещать её в panic message.

Не включать её в telemetry.

Не включать её в crash report.

## 8.2. Пользовательские правила

Пользователь должен иметь возможность:

* добавить собственное регулярное выражение скрытия;
* указать запрещённые команды;
* указать запрещённые каталоги;
* исключить проект;
* исключить оболочку;
* очистить конкретную команду;
* очистить историю проекта;
* очистить всю локальную базу;
* настроить срок хранения.

Регулярные выражения должны быть защищены от ReDoS:

* использовать безопасный regex engine;
* ограничивать размер входных строк;
* ограничивать количество пользовательских правил;
* валидировать правило перед сохранением;
* предотвращать чрезмерное потребление CPU.

## 8.3. Шифрование

На этапе проектирования необходимо подготовить threat model и ADR по шифрованию.

Требования:

* не изобретать собственную криптографию;
* не хранить ключ шифрования рядом с зашифрованной базой;
* использовать системное защищённое хранилище;
* Windows: подходящий механизм Windows Credential Manager или DPAPI;
* Linux: Secret Service API или совместимое защищённое хранилище;
* иметь понятное поведение, если системное хранилище недоступно;
* не откатываться незаметно к открытому хранению;
* предупреждать пользователя;
* позволять отключить сбор до устранения проблемы.

До внедрения полного шифрования не заявлять, что база полностью защищена.

## 8.4. Буфер обмена

Копирование команд:

* только по действию пользователя;
* с уведомлением;
* без фонового чтения clipboard;
* с возможностью автоматически очистить clipboard через настраиваемое время для чувствительных шаблонов;
* без обещаний абсолютной защиты clipboard.

# 9. Модель угроз

Создать `THREAT_MODEL.md`.

Рассмотреть как минимум:

* вредоносный проект;
* специально сформированное имя файла;
* вредоносный Git branch name;
* вредоносное содержимое истории терминала;
* XSS через отображаемые команды;
* HTML и JavaScript внутри команды;
* shell injection;
* command injection;
* path traversal;
* symlink attacks;
* TOCTOU;
* SQL injection;
* ReDoS;
* log injection;
* CSV injection;
* formula injection при экспорте;
* Unicode spoofing;
* bidi control characters;
* oversized input;
* zip bomb при импорте;
* повреждённая база;
* вредоносный файл импорта;
* подмена обновления;
* dependency confusion;
* supply-chain attack;
* уязвимый frontend dependency;
* вредоносный Tauri plugin;
* чрезмерные Tauri capabilities;
* XSS с переходом к IPC;
* злоупотребление IPC-командами;
* CSRF для локального HTTP-сервера, если он когда-либо появится;
* открытый debug endpoint;
* небезопасные временные файлы;
* слабые разрешения файлов;
* утечка через логи;
* утечка через crash dump;
* DLL search order hijacking в Windows;
* загрузка библиотек из небезопасных путей;
* небезопасный auto-update;
* downgrade attack;
* rollback на уязвимую версию;
* подмена конфигурации;
* локальный пользователь с доступом к профилю;
* malware, уже работающий с правами пользователя.

Честно зафиксировать границы защиты.

Dev Recall не может защитить секреты от вредоносной программы, которая уже выполняется с правами того же пользователя и имеет доступ к его данным.

# 10. Безопасность Tauri

Использовать минимально необходимые Tauri capabilities.

Требования:

* deny-by-default;
* отдельные capability-файлы;
* запрет неиспользуемых API;
* запрет произвольного чтения файлов;
* запрет произвольной записи файлов;

# 16. Работа с памятью и ресурсами

Несмотря на использование Rust, отдельно проверять:

* циклы `Rc` и `Arc`;
* неправильное применение `Arc<Mutex<_>>`;
* накопление event listeners;
* неосвобождённые subscriptions;
* бесконечно растущие caches;
* бесконечно растущие vectors;
* фоновые Tokio tasks;
* незакрытые file handles;
* незакрытые database connections;
* незавершённые child processes;
* watchers, которые не отключаются;

* React effects без cleanup;
* duplicate listeners после навигации;
* удержание больших результатов поиска;

* cancellation token;
* cleanup;

Минимум проверить:

* 8 часов работы;
* многократное открытие и закрытие проектов;

* импорт большого history-файла;

* быстрое переключение экранов;
* закрытие приложения во время импорта;

# 29. Crash handling

Приложение должно:

* корректно обрабатывать panic;
* не скрывать критические ошибки;
* сохранять безопасный технический отчёт;
* не включать секреты;
* не отправлять отчёт автоматически;
* восстанавливать незавершённую операцию;
* отмечать прерванный импорт;
* освобождать lock;
* корректно обрабатывать повторный запуск.

Не использовать panic для обычного управления ошибками.

В production-коде избегать:

* `unwrap()`;
* `expect()`;
* индексирования без проверки;
* непроверенных преобразований;
* игнорирования `Result`.

Исключения допустимы только в тестах или при доказуемом инварианте с комментарием.
